# A 阶段 Intent 与 Memory 交接文档

## 目标

A 阶段负责把用户自然语言请求转换成稳定的结构化约束，并在合并记忆时保证当前输入优先。B 阶段只应消费这些结构化字段和明确的软偏好，不应重新把被否定的历史偏好、已完成服务或上下文锚点解释成新的行程节点。

## 核心输出

`parse_intent()` 和 `constraints_from_intent()` 应至少稳定输出：

- `scene`：当前场景，如 `family`、`couple`、`friends`、`business`。
- `people_count`：参与本次行程的总人数。
- `people`：同行人角色与人数，例如孩子、父母、同学、客户、同事。
- `time`：主规划窗口，包含 `window`、`start_time`、`end_time`、`duration_range`。
- `explicit_constraints`：当前请求中明确说出的硬约束，分为 `dietary`、`accessibility`、`logistics`、`time_anchors`。
- `constraints.hard`：必须满足的餐饮、健康、安全、可达性等约束。
- `constraints.soft`：可以优化但不能压过当前硬约束的偏好。
- `constraints.avoid`：当前明确拒绝的活动、餐饮类型、历史偏好或路线风格。

## 当前输入优先规则

当用户明确否定旧偏好时，A 阶段必须把相关标签从正向偏好中移除，并写入 `avoid` 或记忆抑制信号。

覆盖示例：

- `孩子今晚放外婆家不带`：不得产生 child companion，也不得激活 `family_care`。
- `不要按亲子路线`：不得把 `亲子`、`儿童友好` 当成活动或筛选要求。
- `别按以前的低卡轻食`、`不想被低卡减脂限制`：不得激活 `health` 记忆，不得把 `low_calorie`、`light_food` 放入餐厅硬需求。
- `也别随便换成普通火锅烧烤`：`火锅`、`烧烤` 应保留在 `avoid`，不能成为 restaurant required tags。

## 人数解析规则

显式总人数优先于后续单人例外。

示例：

- `我们5个大学同学，一个人吃素`：`people_count=5`，不能被 `一个人吃素` 改写为 1。
- `6个人17:20在人民广场集合`：`people_count=6`，数字后紧跟时间也应识别为总人数。
- `我和同事陪两个外地客户`：`people_count=4`。
- `两个外地同学来上海，我送他们到虹桥`：`people_count=3`，包含用户本人。
- `孩子在外婆家不带，我和两个朋友`：不得把外婆计入同行人。

## 时间与服务锚点

A 阶段必须区分主规划窗口、固定锚点和已完成/已预约服务。

示例：

- `17:40做完口腔处理出来，20:45前回酒店`：主窗口是 `17:40-20:45`，牙科和酒店返回是锚点，不是待预约服务。
- `足球试听课已经约好了，18:45以后附近吃饭，20:30前回家`：主规划窗口是 `18:45-20:30`，足球培训是已有锚点，不得生成 `sports_training` 待订节点。
- `后天朋友13:10到虹桥站，20:00前往浦东机场`：`后天` 应是 `day_after_tomorrow`，`origin=虹桥站`，`end_time=20:00`。
- `周六9:30出发，周日15:30回到`：两日主窗口不得被中间 `14:00-16:00` 休息锚点覆盖。

## 饮食与可达性约束

饮食和身体约束应进入 `explicit_constraints` 与 `constraints.hard`，不能只作为软偏好。

覆盖词包括：

- 过敏与禁忌：`坚果过敏`、`乳制品过敏`、`避开海鲜`、`不吃猪肉`、`不吃牛羊肉`。
- 饮食风格：`不辣`、`少盐`、`少糖`、`无酒精`、`软一点`、`别太硬`。
- 可达性：`轮椅`、`电梯`、`少楼梯`、`少步行`、`术后`、`膝盖不好`。

## 给 B 阶段的消费约定

B 阶段应遵守：

- 用 `time.start_time/end_time` 作为主调度边界。
- 用 `explicit_constraints.time_anchors` 表示固定票、接送、休息、已预约服务等不可漂移锚点。
- 只把当前正向活动或餐饮意图生成 itinerary roles。
- 对 `avoid` 中的角色或餐饮组做硬排除。
- 将已完成、已预约、不可直接代办的服务作为 anchor 或 unsupported guidance，不要变成可执行节点。
- 当只有部分节点可执行时，保留 unsupported guidance，同时尽量为受支持的餐饮/活动节点生成可执行候选。

## 验证要求

新增或修改 A 阶段逻辑时，至少做三类检查：

- 目标样例直接解析：确认人数、时间窗、硬约束、avoid 和 memory active values。
- 相邻回归：no-child、同学/客户人数、饮食禁忌、跨日窗口、已预约服务锚点。
- 完整 agent bounded rerun：验证 B/C 不再收到明显错误的 A-stage 字段。
