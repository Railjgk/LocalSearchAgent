把“用户真正关心什么”从隐含话语里稳定提取出来，再用可解释权重影响本地生活规划。

本报告建议采用保守但可验证的第一版：沿用现有规则 intent parser，新增 current-turn value probe， 并补齐 memory manager 的 current-first 合并与审计能力。这样既能支撑产品侧的个性化体验，也能给研究侧留下清晰的 数据、评估和模型升级路径。

核心业务指标： 上线前重点验证“方案采纳率提升、二次修改率下降、解释满意度提升、冲突场景投诉/负反馈下降”四类信号； MVP 的硬验收以离线 pairwise 胜率、证据命中率和 current-first 正确率为准。
≥60% 人工 pairwise 中 `intent + probe` 胜过 `intent only` 的比例。
≥0.90 Evidence span hit rate：核心 value 必须能回指用户原话。
≥95% 冲突样本中 current-first 策略正确率，避免历史记忆带偏。
0 回归 `value_probe` 接入不得降低原 intent parser 回归测试通过率。
一句话结论： 这不是“再做一个分类器”，而是在本地生活规划链路中补上“价值层”的可计算接口： intent 解决“要做什么”，value probe 解决“为什么这样选更适合这个人”，memory 解决“什么时候可以用历史偏好补充”。 当前代码已有 value memory 投影雏形，但 current value、value_sources 与 value_merge_trace 仍是本轮需要补齐的能力。

1. 背景：本地生活推荐正在从“找结果”走向“做决策”

本地生活场景里的用户请求往往不是单一检索词，而是一个带人、时间、预算、路线、风险偏好和情绪目标的决策任务。 例如“今天下午和老婆孩子出去玩，孩子5岁，老婆最近在减肥”并不只是“亲子活动 + 轻食餐厅”的检索， 它还隐含了家庭照顾、健康、便利、少排队、低强度等价值约束。

现有系统已经具备 A-stage 到 B/C-stage 的完整链路：`intent_parser -> memory_manager -> scenario_planner -> candidate_generator -> constraint_filter -> plan_optimizer ...`。这说明项目不是从零开始，而是在已有规划链路中补一层 更细的价值信号。

对产品经理意味着什么

用户不会总是说“我重视家庭友好、少折腾、健康饮食”。产品需要把这些隐含诉求转成可解释的排序和过滤行为， 才能让推荐看起来更懂人，而不是只会堆热门 POI。

对 AI 研究员意味着什么

价值不是单轮槽位，也不是长期画像的同义词。它需要有标签定义、证据片段、置信度、冲突处理和下游消融验证， 否则无法判断模型是否真的学到了可迁移的用户价值。

现有依据： 当前仓库已在 `src/state.py` 定义 `ValueMemoryItem`，已在 `src/memory/policy.py` 把 `value_profile` 投影为 `value_weights` 与 `score_weights`，并在运行记录中显示这些权重会出现在 planner 约束里。

2. 痛点：只有 intent 和 memory 还不够

痛点 真实表现 为什么影响美团式本地生活体验 本方案对应解法
隐含价值被压扁成标签 “老婆减脂”能转成 `low_calorie`，但很难说明健康价值如何影响餐厅、菜单、路线和解释。 用户觉得结果有相关性，但不一定觉得“懂我”。 新增 `value_probe`，输出 `health` 分数、置信度和证据片段。
历史画像可能覆盖当前意愿 历史里有健康偏好，但用户今天明确想吃火锅；如果 memory 权重过强，推荐会显得自作主张。 本地生活决策强时效，当前场景常常比长期偏好更重要。 采用 `current explicit intent > current value probe > recent memory > long-term memory > defaults`。
排序理由难审计 `score_weights` 已存在，但 value 从哪里来、为什么参与或不参与不够透明。 PM 难定位体验问题，算法同学难做消融，客服/解释链路也缺证据。 输出 `value_sources`、`effective_value_profile` 和 `value_merge_trace`。
Prompt-only 分数不可校准 即使要求 LLM 给出 0-1 分数，同样的“吃点清淡的”在不同对话里也可能被打成不同 `health` 强度。 分数波动会直接改变 `score_weights`，进而影响排序、解释和后续个性化沉淀，线上表现难复盘。 用 `value_probe` 固定标签定义、证据、分数区间和标定集，让同类表达的价值强度可比较。
直接上模型风险大 闭源 API、embedding regressor、activation probe 容易增加成本、非确定性和概念误用。 MVP 验收会被环境、prompt drift、标注不足拖慢。 第一阶段只做规则 probe，训练和模型 provider 作为后续可插拔增强。

3. 方案主张：当前轮 Value Probe + Current-first Memory Merge

方案保持主图结构不变，只增强 `intent_parser_node` 和 `memory_manager_node`。`intent_parser_node` 继续负责结构化 intent， 额外产出当前轮 `value_probe`；`memory_manager_node` 需要新增把当前 value 与历史 `value_profile` 分层合并的能力，并投影为后续模块统一读取的 `effective_value_weights` 和 `score_weights`。

当前实现缺口： 现有 `apply_value_memory` 主要是把历史 `value_profile` 投影到 constraints 和 `score_weights`， 还没有真正合并 current-turn `value_probe`，也没有稳定输出 `value_sources` 与 `value_merge_trace`。 因此 current-first 在本报告中是 Phase 2 的待补能力，不应表述为已完成能力。
为什么不是 prompt-only： Prompt 可以生成 value 文案，甚至可以被要求输出分数，但没有标定集、稳定分数区间和回归测试时， 这些分数很难跨对话比较。`value_probe` 的优势是把“吃点清淡的”这类表达映射到可复现的 `health` 强度、证据和置信度，让它能安全进入 `score_weights`、个性化策略和后续消融评估。

关键边界： 计划中的第一版不是 hidden-state probing。对外建议称为 `Intent Value Probe` 或 `Current-Turn Value Probing`； 只有未来真正读取开源模型内部 activation 时，才使用 activation probe 叙事。

4. 产品价值：它解决的是“为什么这个方案适合我”

提升推荐满意度

同样是亲子出行，带 5 岁孩子、伴侣减脂、预算敏感、害怕排队会对应不同方案。 Value Probe 让排序目标从“场景匹配”进一步变成“场景 + 人 + 当下状态匹配”。

提升解释可信度

解释不再是泛泛地说“适合亲子”，而可以说“因为你提到孩子 5 岁和伴侣减脂，所以优先选择低强度活动和低卡餐厅”。 证据片段来自用户原话，解释更自然。

降低误个性化风险

当前输入优先于长期记忆，避免“历史上你爱轻食，所以今天也必须轻食”的强行个性化。 对本地生活这种强场景任务，这个边界非常重要。

稳定量化价值强度

Prompt-only 可以说“用户想吃清淡”，但不一定能稳定给出跨会话可比较的 `health` 强度。 Probe 用固定 taxonomy、证据和标定规则约束分数，让“偏清淡”和“强减脂”在排序上有可控差异。

本项目优先提升的业务指标

5. 技术可行性：代码已有接点，改动集中且可回滚

从现有仓库看，方案具备三个基础：第一，图结构已经有稳定的 A/B/C 链路；第二，intent parser 已经能把隐含话术转成结构化约束； 第三，memory policy 已经能把 value memory 投影到 `score_weights`，而 plan optimizer 已经读取这些权重。需要谨慎的是： 当前链路证明“value 可以影响排序目标”，但还没有证明“current value 已经完成合并审计”。

排序影响边界： `plan_optimizer` 当前读取 `constraints.score_weights` 覆盖默认目标权重，但 `_derive_weights` 会把 `health` alias 到 `group_fit`。因此报告中不应说“health 已经作为独立 objective 排序”，更准确的说法是： 当前 `health` 通过目标权重映射间接影响排序；是否新增独立 health objective 是后续产品与算法需要共同确认的决策。
依据 当前事实 对方案的支撑 / 待补点
图结构 src/graph.py 中 A-stage 顺序是 `intent_parser -> memory_manager -> scenario_planner`。 新增 value probe 不需要新节点，减少主链路风险。
Intent parser intent_parser.py 已解析孩子、伴侣减脂、距离、预算、排队等隐含表达。 可在 `parse_intent` 后追加 `probe_current_turn_values`，不破坏原有 intent/constraints。
Memory policy policy.py 已有 `apply_value_memory`、`select_active_value_memory`，并生成 `value_weights`、`value_confidence`、`score_weights`。 支撑历史 value 投影；待补 current `value_probe` 与 memory 的分层合并、来源记录和冲突 trace。
Plan optimizer plan_optimizer.py 的权重推导会读取 `constraints.score_weights` 覆盖默认目标权重；其中 `health` 当前映射到 `group_fit`。 Value Probe 的结果能间接影响下游排序；若产品要求健康独立排序，需要新增或拆分 health objective。

6. 成功标准：上线前必须证明什么

本项目的验收不是“多抽出几个 value 标签”，而是证明 value 信号能在不伤害原 intent 链路的前提下， 让方案更贴合当前用户、解释更可追溯、历史记忆不越权。

验收项 硬阈值 样本与方法 失败标准
Value 抽取准确性 四个 MVP value 的 Macro F1 ≥ 0.75；二分类 AUC ≥ 0.80。 人工标注测试集，低频和无 value 样本单独报告。 任一高频 value 明显塌缩，或靠泛化触发导致误报不可控。
Value 分数可校准 同一强度 bucket 内 score 标准差 ≤ 0.08；强弱分组单调性 ≥ 95%。 用“吃点清淡的”“老婆减脂”“严格低卡”等锚点样本标定 `health` 强度。 同义表达分数漂移过大，导致相同诉求在不同会话中触发不同排序行为。
解释证据可追溯 Evidence span hit rate ≥ 0.90。 每个命中 value 必须有可回指原话的 span；无证据不得输出高置信。 解释无法指向用户原话，或第三方信息被扩写成长期画像。
下游方案收益 人工 pairwise 中 `intent + probe` 胜过 `intent only` 的比例 ≥ 60%。 盲评同一输入下两套方案，评审只看方案质量与解释，不看系统标签。 胜率低于阈值，或提升只来自更长文案而非真实方案变化。
Current-first 冲突处理 冲突样本中 current-first 策略正确率 ≥ 95%。 构造“今天想吃火锅 + 历史健康偏好”等 current 与 memory 冲突样本。 历史记忆覆盖当前明确输入，或 trace 未记录 memory 未应用原因。
Intent 链路无回归 原 intent parser 回归测试通过率不下降；关键字段准确率下降 ≤ 1pp。 复用现有 intent 回归集，新增 value 字段必须是兼容扩展。 `value_probe` 接入导致现有 constraints、scene_type 或同行人解析回退。

7. 数据与评估方案：先证明有用，再证明更聪明

第一阶段的评估重点不是模型 SOTA，而是链路可用、解释可信、下游排序有可观测差异。 模型训练应在规则版形成 baseline 后进行，否则很难判断“训练模型好”还是“prompt/规则刚好覆盖”。

数据集 最低规模 覆盖要求 标注人和分歧处理
Value 抽取标注集 600 条本地生活请求，按 60/20/20 切分 train/dev/test。 四个 MVP value、无 value、multi-value、低频表达、边界反例都要覆盖。 2 名标注员独立标注，PM 或算法负责人仲裁；记录 Cohen κ，低于 0.65 需重写标签定义。
Pairwise 方案评审集 120 组输入，每组生成 `intent only` 与 `intent + probe` 两套方案。 亲子出行、约会、朋友聚会、轻食/火锅冲突、预算敏感和便利优先。 3 名评审盲评，取多数票；评审理由归因到方案、排序或解释。
Current-first 冲突集 60 条 current 与 memory 冲突样本。 健康 vs 明确品类、预算 vs 品质、便利 vs 探索、家庭画像 vs 单人场景。 工程输出 trace，PM/QA 判断策略是否正确；错例必须进入回归集。
隐私与写入审计集 80 条含第三方健康、儿童年龄、家庭成员、敏感暗示的样本。 区分短期状态、长期画像候选、禁止写入项和需要用户确认项。 PM、法务/合规或数据治理同学共同确认规则；未确认前不进长期记忆。
评估层 指标 通过标准 失败后动作
抽取准确性 Macro F1 / AUC / 低频标签单独报告 Macro F1 ≥ 0.75，AUC ≥ 0.80；低频 value 不并入高频 value 粗暴兜底。 补反例、拆规则、降低低置信输出，不进入灰度。
分数一致性 Pearson / Spearman 与 0-6 人工强度标注的相关系数 ≥ 0.55。 降级为二分类标签，不把强弱分数用于排序权重。
跨会话可比较性 Anchor phrase stability / bucket monotonicity 同一 value 强度 bucket 内 score 标准差 ≤ 0.08；更强表达的平均分不得低于弱表达。 冻结分数到规则档位，只输出低/中/高，不直接使用 LLM prompt 数字。
解释能力 Evidence span hit rate Evidence span hit rate ≥ 0.90；高置信 value 必须有证据。 关闭解释中的 value 文案，只保留内部 trace。
特异性 Matched vs mismatched diagonal dominance 对应 value 的语料得分高于非对应 value 语料，混淆矩阵需展示主要错因。 重写 taxonomy 边界，尤其是 `family_care` 与 `convenience` 的重叠。
下游收益 Downstream ablation `intent + probe` pairwise 胜率 ≥ 60%；`intent + probe + memory` 不低于 probe-only。 只保留 probe 作为解释信号，不进入排序权重。
冲突处理 Current-first accuracy 冲突样本正确率 ≥ 95%，且每个 memory 抑制都有 trace。 关闭 memory 补充或降低长期画像上限，直到 trace 可审计。

8. 上线边界、灰度与隐私记忆策略

MVP 应该以可开关、可回滚、可降级为前提进入灰度。任何 value 结果都不能阻塞主链路： 低置信、无证据或 merge trace 异常时，系统必须回退到现有 `intent + memory` 行为。

上线与降级边界

边界项 策略 回滚 / 降级方式 监控信号
Feature flag 新增 `ENABLE_VALUE_PROBE`、`ENABLE_VALUE_MERGE_TRACE`、`VALUE_PROBE_RANKING_WEIGHT` 三个开关。 先关排序权重，再关 probe 输出；保留日志便于复盘。 异常率、延迟、空值率、trace 缺失率。
低置信或空 probe `confidence < 0.55` 或无 evidence 时，不进入排序权重，只作为 debug trace。 回退到现有 `intent + memory`；解释文案不展示 value。 低置信占比、无证据高分占比。
Merge trace 失败 trace 生成失败不得影响主链路；当前请求仍按现有 constraints 运行。 关闭 current-memory merge，仅保留历史 `apply_value_memory`。 trace 序列化失败、冲突原因缺失、schema 校验错误。
灰度范围 先离线 replay，再内部账号，再 5% 亲子/周末规划流量；不直接全量。 按用户级 feature flag 回滚，保留对照组用于比较。 采纳率、修改率、负反馈、规划耗时。
排序权重上限 MVP 中单个 value 对目标权重只做小幅调整，避免越过 hard constraints。 将 `VALUE_PROBE_RANKING_WEIGHT` 置 0，value 仅用于解释和日志。 被 value 改写的 top plan 占比、异常错排样本。

隐私与记忆写入策略

信息类型 短期状态 长期画像 删除与审计
用户本人当轮偏好，如“今天想清淡点”“别太贵”。 允许进入本轮和短期会话状态，默认 TTL 为本次会话或 24 小时。 多轮重复且置信度高时才可作为长期候选，需保留证据来源。 用户可清除偏好记忆；trace 记录来源、时间和 TTL。
第三方健康状态，如“老婆最近在减肥”。 只用于本轮规划和短期解释，默认不跨会话保存。 不自动写长期画像；除非用户明确要求记住，且产品/合规确认可存。 解释中避免扩写健康结论；删除时同步清理 evidence。
儿童年龄和家庭成员信息，如“孩子 5 岁”。 可用于本轮儿童友好和安全约束。 默认不长期保存精确年龄；可保存抽象场景偏好需用户可见可删。 提供“删除家庭信息/偏好”的入口，审计写入原因。
敏感或推断性信息，如健康诊断、收入、身份状态。 原则上不推断；仅使用用户明确提供且与本轮任务必要相关的信息。 禁止自动写入长期画像。 触发敏感规则时记录为 redacted trace，不进入推荐解释。
产品底线： current-turn value 默认短期有效；第三方健康、儿童年龄等信息不自动长期沉淀； 长期画像写入需要更高置信度、多轮重复证据，或用户显式授权。

9. 资源排期：四阶段推进，避免一次性过度建设

阶段 Owner / 工期 依赖与阻塞项 主要产出 完成标准 / 回滚方式
Phase 1：数据定义 + 规则 Probe 接入 算法 1 人天，后端 2 人天，PM 1 人天。 需要 600 条标注样本的标签规范；阻塞项是 taxonomy 边界未定。 新增 `src/value_probe/schema.py`、`src/value_probe/rules.py`；`intent_parser_node` 返回稳定 `value_probe`。 空输入、无命中、多 value 命中均返回稳定 JSON shape；开关关闭后行为等同原链路。
Phase 2：Current-first Merge 后端 2 人天，算法 1 人天，QA 1 人天。 依赖 Phase 1 schema；阻塞项是隐私写入规则和冲突策略未确认。 拆分 `merge_current_and_memory_values` 与 `project_values_to_score_weights`，保留 `apply_value_memory` 兼容入口。 `effective_value_weights`、`value_sources`、`score_weights`、`value_merge_trace` 同时存在；失败时回退历史 `apply_value_memory`。
Phase 3：离线评估与 Demo PM 1 人天，算法 2 人天，QA 1 人天。 依赖 pairwise 评审集和 current-first 冲突集；阻塞项是人工评审资源。 构造 `intent only`、`intent + probe`、`intent + probe + memory` 的消融输入和评审表。 达到 Macro F1、Evidence、pairwise、current-first 阈值；不达标则 value 只保留日志和解释，不进排序。
Phase 4：小流量灰度 后端 1 人天，QA 1 人天，PM 1 人天。 依赖 feature flag、监控看板、用户级回滚；阻塞项是隐私删除入口未确认。 先内部账号，再 5% 亲子/周末规划流量；保留对照组。 采纳率、修改率、负反馈不劣于对照；异常时先关排序权重，再关 probe。
MVP 之后：模型增强 算法 3-5 人天起，视数据量和 provider 而定。 依赖稳定 baseline、足够训练数据和明确成本预算。 接 embedding regressor、闭源 provider 或未来开源 activation probe。 训练版必须在抽取、解释、下游消融上优于规则 baseline，否则不替换。

最小测试集

  • `intent_parser` 能在同一输入下返回 `intent`、`constraints`、`value_probe`。
  • 当前输入含“老婆在减脂”时，`health` 来源必须是 current probe，而不是 memory。
  • 当前输入未说“别折腾”但历史有 `convenience` 时，只能以补充权重进入 `effective_value_weights`。
  • 当前输入和 memory 冲突时，当前输入优先，`value_merge_trace` 记录 memory 未应用原因。
  • 后续 planner 只读取合并后的 `constraints.score_weights`，不直接依赖原始 memory value。

10. 风险边界：主动把容易被质疑的点讲清楚

可能质疑 建议回应 补充论据
这是不是换个名字的关键词规则？ 第一版确实是规则 baseline，但重点是定义 value contract、evidence、merge trace 和下游消融。没有稳定 baseline，就无法证明后续模型增强有效。 现有计划明确 Phase 1 不接模型，Phase 4 才接 embedding 或外部 provider。
为什么不直接让 LLM 做 intent + value 一次性解析？ 可以作为后续 provider，但 MVP 先避免 API 成本、prompt drift、schema 校验和回归测试不稳定。接口先稳定，provider 可以替换。 现有 `build_intent_prompt` 已保留模型替换入口，但当前 demo 依赖规则保证离线可运行。
Memory 会不会带偏当前请求？ 这是本项目必须补齐和验证的能力，不应说已经完全具备。设计上历史只在当前缺失时弱补充，短期补充建议不超过 0.45，长期画像更低，并记录 trace。 验收规则：冲突样本 current-first 正确率 ≥ 95%；失败则关闭 memory 补充或只保留日志。
Value 标签会不会太主观？ 通过 evidence span、边界样本、冲突样本、非触发词和权重上限降低主观性。低频 value 单独报告，不把所有东西混成一个“用户偏好”。 MVP 只启用四个高频、可解释、可行动的 value，并用 Macro F1 ≥ 0.75 做门槛。
是否涉及隐私或伦理风险？ 涉及。伴侣减脂、孩子年龄、家庭成员都不能无条件长期沉淀。MVP 默认 current-turn value 短期有效，第三方健康和儿童年龄不自动写长期画像。 上线前需要删除入口、TTL、写入审计和敏感信息 redaction；未完成则不进灰度。
Health 是否已经独立影响排序？ 当前更准确的说法是“通过 `score_weights` 映射间接影响”。代码里 `health` alias 到 `group_fit`，是否拆出独立 health objective 需要另做产品/算法决策。 本报告不把当前实现包装成独立 health 排序目标。
研究创新点在哪里？ 创新不在第一版规则本身，而在本地生活决策中把抽象价值、当前轮证据、历史记忆和下游多目标优化连成可评估链路。 可用 A-A/A-C/C-C 标注和下游 ablation 形成研究闭环。
评审时不要过度承诺： 第一阶段不替换现有 intent parser，不做闭源模型 activation steering，不训练 embedding regressor， 不把单轮 probe 结果直接写成长期画像，也不声称已经实现 BACH-V 式内部激活探针。

11. 建议讲稿：10 分钟评审结构

开场 1 分钟： 我们要解决的问题不是“再多抽几个槽位”，而是本地生活规划里用户隐含价值缺少一个可计算接口。 比如“老婆最近在减肥、孩子 5 岁、别太折腾”，这些话背后对应健康、家庭照顾和便利性。 如果系统只能抽到标签，推荐会相关但不一定贴心；如果直接依赖长期画像，又可能覆盖用户今天的明确意愿。

方案 3 分钟： 我建议第一版保持主链路不变，在现有 intent parser 后加 current-turn value probe。 它输出 value_id、score、confidence 和用户原话 evidence。这里相对 prompt-only 的优势是分数可标定： 同样的“吃点清淡的”应该落在稳定的 `health` 强度区间，不能每轮随机影响排序。 现有代码已经有 value memory 到 `score_weights` 的投影， 但还需要补 current-turn value 与 memory 的 current-first merge：当前明确 intent 最高，其次是当前 value probe， 再其次才是近期和长期 memory。最终只把合并后的 `effective_value_weights` 和 `score_weights` 给 planner/ranker 使用。

产品价值 2 分钟： 这能让推荐从“场景匹配”变成“场景 + 人 + 当下状态匹配”。对 PM 来说，验收点不是模型参数， 而是方案采纳率、二次修改率、解释满意度和冲突负反馈。上线前的硬门槛是 pairwise 胜率 ≥ 60%、 evidence 命中率 ≥ 0.90、冲突样本 current-first 正确率 ≥ 95%。

技术可行性 2 分钟： 当前仓库已经有稳定的 `intent_parser -> memory_manager -> scenario_planner` 链路； memory policy 已经能把 `value_profile` 投影成 `score_weights`；optimizer 也读取这些权重。 但 `health` 当前通过 `group_fit` 间接影响排序，不是独立 health objective；所以第一版只是补 current value 来源和合并审计，不需要重构主图。

收束 2 分钟： 研究上，我们借鉴 BACH-V 的 A-A/A-C/C-C 价值理解框架和 specificity 评估思路，但第一版只做 rule/text probe。 等规则 baseline 和消融 demo 稳定后，再上 embedding 或 activation probe。这样既能快速给产品价值，也能让研究升级有坚实对照组。
